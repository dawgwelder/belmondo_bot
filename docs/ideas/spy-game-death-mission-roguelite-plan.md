# Death Mission: roguelite для Смертельной операции

Статус: первоначальное предложение; основная механика реализована локально.
Актуальные правила, результаты симуляции и включение описаны в
[runbook](../runbooks/spy-game-death-mission.md).
После уточнения продукта вход предлагает два режима: мгновенный all-in либо
личную миссию. В v3 победа удваивает ставку, а бонус Tier 3 ×1 либо Tier 4 ×1 доступен
при ставке минимум пяти агентов выбранного тира или выше. Старые v1/v2
сохраняют прежние выплаты. Экономический гейт v3 ограничивает полную выплату,
включая бонус, коэффициентом 1,15 от ставки; актуальные числа и условия
описаны в runbook. Историческое требование ниже «не выше старого all-in»
заменено этим явным допуском.
Отдельного тренировочного UI пока нет; есть офлайн-симулятор.

Ниже сохранена исходная проектная проработка; при расхождении приоритет у runbook.
Основано на [исходном плане](spy-game-html5-mole-death-plan.md) и текущем коде
на 2026-09-04. Все новые числа ниже — кандидаты для прототипа.

## 1. Основное решение

Превратить `death_operation` в короткую пошаговую вылазку: игрок ставит сеть,
выбирает маршрут, собирает временные улучшения и решает, эвакуироваться с
потерями или пройти финальный объект ради удвоения сети. После поражения
сохраняются открытые тактики и сведения о противнике, но не сборка забега.

Это отдельная версия правил `roguelite_v1`. Фиксированные 35% принадлежат
старому `all_in_v1`: в новом режиме победа определяется прохождением маршрута.
Добавлять в конце ещё один скрытый бросок на 35% нельзя — он обесценит решения.

Рекомендую сохранить all-in как узнаваемую особенность Смертельной операции.
Для проверки удобства и баланса сначала нужен тренировочный режим с виртуальной
ставкой: без списаний, наград и постоянного прогресса. Если all-in мешает
повторным забегам, отдельным следующим решением станет экспедиционный отряд
с ограниченной ставкой; это изменит экономику и не входит в этот вариант.
Тренировка получает собственный seed и не открывает карту боевого события.

Почему это roguelite:

- маршрут и предложения улучшений меняются между событиями;
- комбинация тактики и находок меняет выгодные решения;
- поражение завершает забег и уничтожает его улучшения;
- между забегами остаются новые варианты старта и знания о комнатах;
- опыт игрока помогает оценивать риск, а не только быстрее нажимать кнопку.

## 2. Что уже есть и что необходимо изменить

| Сейчас в репозитории | Следствие для реализации |
|---|---|
| `SpyRepository.run_death_operation` подтверждает состав и сразу рассчитывает результат | Разделить резервирование ставки, игровые действия и расчёт итога |
| `user_agents` принадлежит пользователю, без `chat_id` | Ставка общая для всех чатов; нужен глобальный запрет второго активного забега |
| `game_events` допускает только одно `active` событие на чат | В MVP забег занимает этот слот до завершения, максимум 15 минут |
| Обычный срок события — 3 минуты | Отделить срок входа от срока уже начатого забега |
| `reconcile` и `_expire_row` закрывают просроченные события | Сначала рассчитывать активный забег и его ставку, затем закрывать событие |
| `start_html5_game` уже различает Перехват, Тайник и Крота | Расширить существующий диспетчер; не создавать второй backend |
| В `event_participants` допустимы только `pending` и `resolved` | Подробное состояние хранить в новой run-таблице |
| `economy_history.action` ограничен `exchange` и `prestige` | Не вставлять туда новые action без миграции; использовать отдельный журнал ставки |

Сохраняем один `SpyGameService`, один HTTP listener и одну SQLite-базу.
Внешний API событий остаётся `death_operation`; переименование в
`death_mission` не требуется. Версия механики фиксируется в payload события.

## 3. Один забег глазами игрока

1. В группе появляется «Смертельная операция». Вход открыт 3 минуты.
2. Игрок видит точную ставку по типам агентов и правила исходов. Выбирает одну
   стартовую тактику из открытых. Предпросмотр ничего не списывает.
3. На отдельном экране подтверждает отправку всей доступной сети.
   Первый подтверждённый старт занимает событие; остальные получают `lost_race`
   без потери агентов. Открытие экрана само по себе слот не занимает.
4. Проходит пять узлов маршрута. Перед каждым выбирает одну из двух комнат,
   а внутри — одно из двух-трёх действий. Находки формируют сборку забега.
5. После третьего узла открывается аварийная эвакуация. Можно вернуть половину
   каждого типа поставленных агентов или продолжить ради полной победы.
6. Шестой узел — финальный объект из трёх коротких фаз. Прохождение с
   положительным состоянием группы даёт состав ×2 и один случайный Tier 3.
7. На итоговом экране: что потеряно/получено, какие решения привели к исходу,
   что открыто для следующей вылазки.

Целевая длительность — 4–7 минут активной игры; жёсткий срок — 15 минут от
подтверждения старта. Это гипотеза для UX-проверки. Нет таймеров реакции на
отдельном ходе. Сохранение выполняется после каждого принятого действия.

В первом релизе один участник на событие, как сейчас. Кооператив, несколько
личных забегов на одно событие и освобождение группового слота при старте —
отдельные расширения: они меняют частоту наград и работу scheduler.

## 4. Ресурсы и правила хода

| Ресурс | Стартовый кандидат | Значение |
|---|---|---|
| Состояние группы `integrity` | 6 из 6 | При 0 забег немедленно проигран; это не количество агентов |
| Разведданные `intel` | 2, максимум 6 | Расходуются на безопасные обходы и действия финального объекта |
| Тревога `alarm` | 0, шкала 0–6 | Повышает риск; достижение 6 вызывает облаву |
| Модули | 0, максимум 2 | Временные правила, полученные по ходу забега |

Размер и редкость поставленной сети в MVP не увеличивают эти характеристики.
Игрок с одним Осведомителем может освоить механику; большая сеть увеличивает
экономический риск и выигрыш. Экипировка, репутация и уровень агентства не
дают неявных бонусов к действиям.

Для каждой кнопки сервер заранее показывает стоимость, гарантированный эффект,
вероятность осложнения и его точные последствия. Например:

> **Архив под наблюдением.** Состояние 4/6, разведданные 2, тревога 2.
> Подменить пропуск: потратить 1 разведданное, получить 2, тревога +1.
> Вскрыть терминал: получить 2 разведданных; риск осложнения 35% —
> состояние −2 и тревога +1.
> Пройти мимо: без добычи и изменения ресурсов; узел будет пройден.

Кандидат формулы для рискованного действия обычной комнаты:

```text
p = clamp(15 + 10 * danger + 5 * alarm + modifier, 5, 75) процентов
danger ∈ {0, 1, 2}; modifier задаётся только версионированными правилами
```

В примере `danger=1`, `alarm=2`, `modifier=0`. Детерминированные действия
вообще не делают roll. Правила финального объекта задаются его шаблоном.
Сервер не обещает общую вероятность победы в ещё не пройденном забеге.

Порядок одного действия фиксирован: проверить доступность и стоимость →
списать стоимость → определить осложнение по состоянию до действия → применить
эффекты действия и модулей → обработать облаву → ограничить ресурсы допустимыми
пределами → проверить смерть → выдать находку/перейти дальше. При тревоге ≥6
облава наносит 2 урона и устанавливает тревогу 4. В MVP одно действие может
вызвать не более одной облавы; ограничения шаблонов должны это гарантировать.
Смерть имеет приоритет над прохождением финальной фазы и наградой.

Шаблоны не могут требовать отсутствующий ресурс без альтернативы. Отказ от
комнаты расходует узел, поэтому не даёт бесконечно искать более выгодную.
Гарантированно смертельный выбор требует явного предупреждения и подтверждения.

## 5. Маршрут, сборки и финальный объект

Маршрут — пять слоёв по две альтернативы и один финальный объект. Сервер
создаёт его один раз при старте; повторный вход не меняет комнаты, предложения
модулей и случайные исходы. Открыты текущие варианты, типы следующего слоя
и название финального объекта; скрытые исходы не отправляются в браузер.

Начальный набор комнат:

| Комната | Решение |
|---|---|
| Патруль | Потратить разведданные, идти с риском или принять гарантированную потерю состояния |
| Архив | Набрать разведданные ценой тревоги или риска |
| Убежище | Восстановить 2 состояния либо снизить тревогу на 2 |
| Схрон | Взять разведданные либо временную защиту от следующего осложнения |
| Двойной агент | Обменять 1 состояние на 2 разведданных либо уйти |
| Засада | Потратить подготовленный ресурс или принять урон; обязательна доступная альтернатива |

После узлов 1 и 3 игрок выбирает один модуль из трёх. Две выдачи заполняют
два слота; замены и дубликаты в MVP исключены. Выбор сохраняется отдельным ходом.
Убежище гарантированно встречается среди вариантов слоя 2 или 4, а генератор
не допускает маршрут, где пройти к финалу невозможно при любом решении.
Это не гарантия победы для любой выбранной последовательности.

Примеры модулей для прототипа:

| Модуль | Эффект и ограничение |
|---|---|
| Глушитель | Первое положительное изменение тревоги в каждой комнате уменьшено на 1 |
| Бронепластины | Первый полученный урон в каждой комнате уменьшен на 1, минимум до 0 |
| Полевой медик | При выходе из обычной комнаты с состоянием ≤2 восстановить 1; один раз за комнату |
| Перехватчик | При получении разведданных в Архиве получить ещё 1 в пределах лимита |
| Поддельный пропуск | Один раз за забег отменить облаву и установить тревогу 3 |
| Аварийный канал | Открыть эвакуацию после узла 2 вместо 3; доля возврата остаётся прежней |

В MVP достаточно шести модулей, трёх тактик и двух финальных объектов.
Модули не меняют множитель сети, не создают постоянные предметы и не дают
бесконечных циклов восстановления. Расходуемые эффекты хранятся в состоянии.

Тактики задают стартовый обмен ресурсов: «Баланс» = 6 состояния / 2 разведданных,
«Тихий вход» = 5 / 3, «Штурм» = 6 / 1 и одноразовая защита от 1 урона.
Последние две открываются метапрогрессией. Числа требуют проверки: ни одна
тактика не должна быть лучшей на всех типах маршрутов.

Финальные объекты: «Штаб контрразведки» и «Бронепоезд». У каждого три фазы:
проникновение, выполнение задачи, отход. Например, проникновение можно оплатить
двумя разведданными или пройти с риском повреждения. Различаются требования
к ресурсам и тревоге; фазы описаны конечными шаблонами, а не LLM.
Модули с эффектом «раз за комнату» не перезаряжаются между фазами одного объекта.

Пример сборки: «Тихий вход» → Архив → Глушитель → Убежище → Перехватчик.
Игрок собирает разведданные для безопасных фаз Штаба, но остаётся уязвимым к
урону. Альтернатива — «Штурм» с Бронепластинами и Медиком, позволяющий чаще
выбирать силовые проходы. Полезность сборки должна проявляться уже в этом забеге.

## 6. Эвакуация, поражение и постоянный прогресс

| Исход | Возврат из ставки | Дополнительная награда |
|---|---|---|
| Победа `won` | Каждый поставленный тип ×2 | Один Tier 3 из закреплённого bonus pool |
| Эвакуация `extracted` | `floor(amount / 2)` каждого типа | Нет экономической награды |
| Поражение `lost` | 0 | Нет экономической награды |
| Таймаут `timed_out` | Как эвакуация, если она уже открыта; иначе 0 | Нет экономической награды |
| Техническая отмена `cancelled_refunded` | Исходная ставка целиком | Нет награды и прогресса |

Эвакуация доступна между действиями после контрольного узла, включая паузы
между фазами финального объекта. После открытия она не закрывается.
Кнопка показывает точный возвращаемый состав: для единственного агента
округление даёт 0. Нельзя округлять каждый редкий тип вверх.

Закрытие браузера ничего не рассчитывает немедленно и не останавливает срок.
Таймаут использует уже открытое право на эвакуацию. Игрок может получить тот же
результат кнопкой, поэтому ожидание не создаёт более выгодного исхода. До
первого контрольного узла можно сдаться с нулевым возвратом; это подтверждается.

В «Архиве операций» постоянно сохраняются открытые тактики, изученные комнаты
и лучшие результаты. Без новой торгуемой валюты и бесконечного роста здоровья:

- пройти третий узел в трёх разных боевых событиях → открыть «Тихий вход»;
- пережить облаву и затем дойти до третьего узла в одном боевом событии → «Штурм»;
- впервые пройти финальный объект → его досье и косметическая отметка.

Достижения первых двух типов засчитываются даже после дальнейшего поражения;
для технически отменённых и тренировочных забегов не засчитываются. Прогресс
применяется один раз при терминальном расчёте; reopen и повторные HTTP-запросы
не дают дополнительных отметок. Архив принадлежит пользователю глобально,
как агентурная сеть, и не сбрасывается при prestige/основании агентства.

## 7. Экономика: почему нельзя просто сохранить шанс победы 35%

Пусть `S` — условная стоимость ставки, `B` — средняя стоимость бонусного Tier 3.
Это аналитические веса, а не обещанный внутриигровой курс обмена.

```text
Старый ожидаемый возврат = 0.35 * (2S + B) = 0.70S + 0.35B
Новый ожидаемый возврат ≈ 2*p_win*S + 0.5*p_extract*S + p_win*B
```

`p_extract` включает таймауты с открытой эвакуацией; округления в этой формуле
опущены и в симуляторе считаются по каждому типу точно. Из возврата нужно вычесть
`S`, чтобы получить ожидаемое изменение баланса. Если оставить победу 35% и
добавить эвакуацию, ожидаемый возврат вырастет.

Для иллюстрации, а не как результат проверки: 30% побед, 20% эвакуаций и 50%
нулевых возвратов дают примерно `0.70S + 0.30B`. Близость к старой средней
не доказывает баланс: опытные игроки выбирают действия лучше случайных, а при
маленькой ставке бонус Tier 3 доминирует над потерями.

До beta нужен воспроизводимый симулятор на том же движке:

- фиксированный набор минимум 10 000 seed на финальную проверку; отдельный набор
  для настройки, чтобы не подгонять параметры под отчёт;
- политики: случайная допустимая, осторожная, агрессивная, ориентированная на
  сборку и сильная, выбирающая по ожидаемому исходу с доступной игроку информацией;
- каждое стартовое снаряжение и сочетание модулей, оба финальных объекта;
- реальные векторы ставок: 1 Осведомитель, малая смешанная сеть, редкая сеть,
  крупная сеть; точные возвраты и создание/сжигание агентов по каждому Tier;
- доли исходов, интервалы неопределённости, причины смерти, частота выбора
  каждого действия, влияние метапрогрессии и распределение длительности ходов.

Экономический гейт: на каждой выбранной ставке ожидаемый возврат сильной
реализуемой политики не выше старого `all_in_v1` с учётом заранее заданного
допуска и статистической погрешности. Явная доминирующая стратегия — повод
переделать контент. Допуск и веса Tier фиксируются до финальной проверки;
без них денежный баланс не считается подтверждённым. Сырые количества по Tier
в отчёте обязательны независимо от выбранных весов.

Если этот гейт требует чрезмерно частых поражений, сначала пересмотреть
награду ×2/Tier 3 или размер ставки. Не компенсировать проблему скрытой
подстройкой вероятностей под игрока. Возможность пройти без экономического
риска проверяется в тренировке, которая должна использовать те же правила.

## 8. Ставка, конкуренция и жизненный цикл

### Подтверждение и резервирование

`preview` хранит канонический снимок доступных `user_agents` и его hash.
Отдельный `arm` выдаёт короткоживущий одноразовый nonce на конкретные revision,
состав, тактику и версию правил. Удержание кнопки 3 секунды — UX-защита;
авторизация и одноразовость обеспечиваются сервером.

`commit_start` в одной `BEGIN IMMEDIATE` транзакции:

1. Проверяет пользователя, чат, версию события, сроки, nonce и revision.
2. Проверяет, что у пользователя нет активного боевого забега в другом чате,
   а событие ещё не занято другим участником.
3. Сверяет текущий доступный состав с preview. При отличии возвращает
   `STALE_STAKE`, обновляет preview и сбрасывает подтверждение без списания.
4. Переводит точные количества ставки из доступного баланса в escrow забега.
5. Сохраняет seed, маршрут, версию контента, исходное состояние и время конца.
6. Закрепляет участника; событие остаётся `active`, его срок становится сроком
   забега. Остальные preview-сессии получают `lost_race`.

После этого агенты уже на задании. Обещание «закрытие окна не меняет баланс»
относится только к периоду до `commit_start`. После старта действуют правила
возврата из раздела 6, и экран подтверждения обязан объяснять это явно.

Агенты, полученные позднее из других событий, остаются доступными. Они не
попадают в ставку, не удваиваются и не теряются при расчёте забега. Обмены,
дуэли, prestige и основание агентства работают с доступным балансом; escrow
не участвует в оплате. На панели сети отдельно показываются «доступно» и
«на операции», чтобы временное списание не выглядело потерей.

### Состояния

```text
preview -> armed -> in_run -> won | extracted | lost | timed_out
preview / armed -> expired | lost_race
armed -- STALE_STAKE --> preview
in_run -- техническая отмена --> cancelled_refunded
```

Игровая фаза отдельно: `choose_room`, `choose_action`, `choose_module`,
`boss_action`. Доступные действия выводятся из фазы и состояния сервером.
`committed_at` после старта неизменяем; у терминального забега нет нового старта.

`settle_run` атомарно сохраняет исход, закрывает escrow, зачисляет точные
возвраты и бонус, применяет достижения, переводит событие и участника в
`resolved`, создаёт единственную итоговую запись `event_history`. Для совместимости
с текущим кодом `winner_user_id` указывает участника операции даже при проигрыше;
UI определяет победу по outcome. Промежуточные ходы в `event_history` не пишутся.

### Время и восстановление

- До старта действует срок входа события; после старта — неизменный
  `run_expires_at = committed_at + 15 минут`. Повторный вход срок не продлевает.
- Deadline проверяется сервером в каждой мутации, при чтении state, в tick
  и при startup reconciliation; на границе `now >= deadline` ход не выполняется.
- Все пути generic expiry, отмены и администрирования должны распознавать
  активный roguelite до обычного `_expire_row`, чтобы не оставить escrow открытым.
- После рестарта восстанавливается та же ревизия. Просроченный run рассчитывается
  по правилу таймаута; промежуточное отсутствие UI не является отменой ставки.
- Штатное отключение новых запусков не мешает завершить начатые. Экстренная
  административная отмена атомарно возвращает ставку целиком и фиксирует причину.
- При повреждённом состоянии запрещено угадывать исход: запуск блокируется,
  stake восстанавливается из escrow через аудируемую техническую отмену.

## 9. Хранение, движок и API

Новая append-only миграция со следующим свободным номером. `012` уже занята
Кротом; `013` из исходного плана не следует создавать независимо второй раз.

| Сущность | Ключевые поля и ограничения |
|---|---|
| `death_operation_runs` | `id`, `event_id`, `user_id`, `chat_id`, `message_id`, `token_hash`, `status`, `phase`, `revision`, `rules_version`, `content_version`, `rules_snapshot_json`, `stake_hash`, `arm_nonce_hash`, `arm_expires_at`, `seed`, `private_map_json`, `state_json`, `result_json`, timestamps |
| `death_operation_stakes` | `(run_id, agent_type)` PK, `amount > 0`; снимок ставки неизменяем |
| `death_operation_actions` | `(run_id, operation_id)` UNIQUE, request hash, revision до/после, тип действия, результат; append-only |
| `death_operation_ledger` | Уникальные операции `reserve:{run_id}` и `settle:{run_id}`, исход и точные векторы резервирования/возврата/бонуса |
| `death_operation_progress` | `user_id` PK, открытые тактики, версия архива |
| `death_operation_achievements` | `(user_id, run_id, achievement_id)` UNIQUE; факты прогресса |
| `death_operation_outbox` | Уникальный ключ публикации, `run_id`, состояние доставки, `message_id`, число попыток и время следующей попытки |

Для runs нужны `UNIQUE(event_id, user_id)`, уникальный `token_hash`, частичный
уникальный индекс по `event_id WHERE committed_at IS NOT NULL` и по
`user_id WHERE status = 'in_run'`; индекс `(status, run_expires_at)` для tick.
CHECK-ограничения фиксируют разрешённые статусы, положительные версии и
неотрицательную revision. Escrow считается закрытым только при наличии settle
и терминального статуса, записанных одной транзакцией.

Выделить чистый `spy_game/death_mission/engine.py`: на вход состояние, действие,
версионированный контент и источник случайности; на выход новое состояние и
эффекты. Отдельные модули — схемы состояния и конечный набор шаблонов.
Repository отвечает за проверки, блокировку и деньги; service — за общий use
case; HTTP и Telegram только преобразуют запросы и результат.

Случайность не зависит от числа повторных HTTP-запросов: приватный seed
сохраняется при старте; исход привязан к стабильным `node_id`, `phase_id` и
`action_id`. Применять стабильный версионированный алгоритм, а не встроенный
Python `hash()`. Rollback не позволяет получить новый бросок. Seed, скрытые
ветви и будущие предложения модулей не выдаются клиенту или LLM.

```text
GET  /spy-app/api/game/state
POST /spy-app/api/game/death/prepare       # preview / выбор тактики
POST /spy-app/api/game/death/arm
POST /spy-app/api/game/death/commit        # начало забега и резерв ставки
POST /spy-app/api/game/death/action        # комната, действие, выбор модуля
POST /spy-app/api/game/death/extract
POST /spy-app/api/game/death/abandon
```

Все мутации: `operation_id`, `expected_revision`, только идентификаторы
допустимых действий; commit также содержит arm nonce. Сервер определяет
пользователя из bearer-токена, а не из JSON. Для Telegram — из callback user
и серверной привязки сессии. Повторное открытие может ротировать token hash,
но не создаёт новый забег; токен остаётся секретом доступа к конкретному run.
Правила, bonus pool и контент закрепляются на весь забег. Смена settings не
меняет начатую операцию; обработчик предыдущей версии сохраняется до её
завершения. Номер версии сам по себе недостаточен без доступного старого контента.

В транзакции сначала проверяются полномочия и сохранённая операция, затем
revision и новое действие. Повтор ключа с тем же payload возвращает записанный
результат; с другим — `IDEMPOTENCY_CONFLICT`. Две вкладки с разными ключами
на одну revision дают один ход и один `STALE_REVISION`. Ответ на старый retry
содержит revision своего результата; клиент затем загружает актуальный state.

Ошибки состояния (`STALE_STAKE`, `STALE_REVISION`, `RUN_IN_PROGRESS`,
`LOST_RACE`, `EXPIRED`, `INVALID_ACTION`) отображаются отдельно от транспортной
ошибки. После потери ответа клиент повторяет ту же операцию, а не создаёт новую.

## 10. HTML5, Telegram и публикация результата

HTML5 содержит экран ставки, карту, текущую комнату, выбор модуля и итог.
В каждом игровом экране видны состояние, разведданные, тревога, оставшееся
время и доступность эвакуации. Никакой обязательной анимации перед действием.

В Telegram остаётся полноценный пошаговый fallback тех же правил: краткое
состояние и inline-кнопки. Обновляется исходное сообщение операции, а не
отправляется сообщение на каждый ход. Действия после старта принимает только
владелец забега; для остальных — ответ «Операцию уже выполняет другой агент».
Открыть HTML5 после хода в Telegram и обратно можно на той же revision.

Ошибка `sendGame` не должна превращать roguelite-событие в старую лотерею.
Handler смотрит на закреплённую `mechanics_version`; старый `death` callback
не может обойти резервирование и вызвать all-in resolver для нового события.

В группе один итог с исходом и составом возврата, публичные участники — только
`@username`, при необходимости «Скрытый агент». LLM может оформить итог по
уже сохранённому результату, но не генерирует правила или исходы.

Для надёжной публикации нужен persistent outbox с ключом `death-result:{run_id}`,
записанный при settlement. Повторяемое редактирование исходного сообщения —
основной канал итогов: оно не создаёт дубликатов при потере ответа Telegram.
Если нужен отдельный пост, учесть окно «сообщение отправлено, message_id ещё
не сохранён»: ровно одну внешнюю отправку обещать нельзя. Экономический итог
при этом всегда один; сетевые вызовы выполняются после SQL commit.

## 11. Этапы реализации и проверочные гейты

1. **Игровой прототип.** Чистый движок, 6 типов комнат, 6 модулей, 3 тактики,
   2 финальных объекта; фиксированные seed и симулятор. Гейт — понятные
   последствия действий, отсутствие безвыходных шаблонов и отчёт экономики.
2. **Persistence.** Миграция, escrow, preview/arm/start/action/settle, expiry,
   достижения, idempotency. Гейт — транзакционные и конкурентные тесты.
3. **Dev-интерфейсы.** HTML5 и Telegram fallback, тренировочный режим, панель
   зарезервированных агентов. Гейт — полный путь обоими интерфейсами и resume.
4. **Beta.** Online backup с integrity check, выключенные по умолчанию новые
   запуски, один allowlisted чат, ручной spawn, smoke двумя аккаунтами.
   Естественный spawn включать после разбора результатов ограниченной beta.

Новый независимый флаг `SPY_GAME_DEATH_ROGUELITE_ENABLED=false` выбирает правила
только при создании новых событий. Флаг HTML5 выбирает интерфейс. Для уже
созданного события правила закреплены. Выключение флага запрещает новые
roguelite-события, но сохраняет API и resolver для завершения существующих.

Rollback на старый бинарник недопустим при открытом escrow: сначала завершить
забеги или выполнить технический возврат, проверить отсутствие `in_run` и
незакрытых резервов. Миграции и журнал не удаляются. Старый `all_in_v1` остаётся
доступен только для событий со своей версией правил.

Обязательные проверки:

- до commit баланс не меняется; изменившаяся ставка сбрасывает arm;
- два игрока на событие и один игрок из двух чатов не создают два резерва;
- повтор commit, action, extract, timeout и admin cancel не повторяет выплаты;
- обновление страницы, restart и rollback SQL сохраняют карту и исход действия;
- обмены/дуэли/основание агентства не тратят escrow; поздние награды сохраняются;
- действие против timeout или отмены даёт один терминальный исход;
- смерть в последней фазе исключает награду; эвакуация корректно округляет каждый тип;
- забытый выбор модуля и закрытое окно доходят до единого правила timeout;
- generic expiry, отключение чата, неверный payload и restart не теряют резерв;
- SQL-ошибка откатывает состояние, баланс, прогресс, outbox и историю целиком;
- Telegram и HTML5 дают один результат на одном потоке действий;
- старый callback не запускает `all_in_v1` для `roguelite_v1`;
- обучение и техническая отмена не увеличивают баланс или метапрогрессию;
- скрытые seed/roll/токены не попадают в публичный JSON, тексты и логи;
- миграции проходят на чистой и существующей базе, старые игры проходят регрессию.

Beta-метрики: завершение и время забега, смерти по узлам, эвакуации, возвраты
по Tier, выбранные сборки, повторное участие, доля тренировок, ошибки resume,
stale revisions, незакрытые escrow и задержка публикации итогов. Локальные
тесты и симуляции не заменяют Telegram smoke и проверку на сервере.
